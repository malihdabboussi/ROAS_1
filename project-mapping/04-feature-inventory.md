## What This Product Does

ROAS is an **agent-run marketing agency in software form**. A customer's org hires a roster of named
AI "employees" (agents), each with a role, a set of markdown skills, its own memory, and its own
communication channels. Instead of the human doing marketing work in a tool, the human delegates
work to agents, watches it execute, and reviews the output. The code makes this literal: the roster
page is `/team` and the confirmation modal for removing an agent is
`apps/web/src/features/team/components/FireEmployeeConfirmModal.tsx`. Agents are seeded from
templates (`agent_templates`, `agent_employee_templates`, `scripts/seed-system-agents.ts`) and each
one gets a real runtime — a per-user Fly.io machine running `apps/agent-api` plus the vendored
OpenClaw gateway.

The work itself lands in three concentric containers. A **Space** (`spaces`, renamed from `lists`)
is the unit of work: a ClickUp-like container with a per-space `schema` JSONB that declares which
**views** it renders — table, docs, calendar, contacts, missions, media, channels, artifacts,
paid-ads, reporting, ads-research, social-research
(`apps/web/src/features/spaces/views/registry.ts`). A **Program** (`programs`) groups Spaces. A
**Campaign** (`campaigns`) is the older strategic container that Spaces optionally hang off via a
nullable `campaigns.id` → `spaces.campaign_id`. Inside a Space, an item is either a human task or a
**Mission** (`missions`, `mission_subtasks`) — a long-running agent job with a DAG of subtasks,
deliverables, retries, and a transactional outbox that wakes the mission worker.

Agents are not stateless. Everything they learn goes into the **Brain** — a pgvector knowledge
layer with separate families for the user, each agent, the company (`company_cortex_*`), and each
customer (`customer_entities`, `customer_avatars`). Knowledge arrives from meeting transcripts
(Fathom, Fireflies), Slack observation channels, Google Drive, uploaded media, and chat itself, gets
embedded at 768 dimensions, and is retrieved through ~24 paired semantic + `_lexical` search RPCs.
Background "dream ops" consolidate it while nobody is looking.

Output is produced as **artifacts**: ad copy, ad creatives, social posts, blog posts, documents,
presentations, funnel pages, offers, avatars, email sequences. Each artifact type has its own
generation route under `/api/campaigns`-adjacent controllers and its own credit charge. Artifacts
are viewable per-Space, per-Campaign, and in a global `/artifacts` library. Distribution goes out
through 40+ integrations — Meta ads, Slack, Telegram, SendGrid email with its own domain
authentication, published funnels on customer domains via Cloudflare + Vercel, and public agent
widgets on `*.agents.roas.io`.

Who uses it: (1) **marketing agencies** — the `/clients`, `/client-campaigns`, `/launches` surface
is an agency console, and `organizations.account_type` is literally `team | agency`; (2) **in-house
marketing teams** inside a single org; (3) **ROAS platform staff**, via a separate `apps/admin` app
and an impersonation system; (4) **anonymous end users** of a customer's published funnels, forms,
and public agent chat widgets. Self-serve signup is closed —
`apps/web/src/middleware.ts:95` redirects `/register` → `/login` whenever
`NEXT_PUBLIC_WAITLIST_MODE !== 'false'`, so entry is by waitlist, invite code, or org invitation.

### Chat & Agent Runtime

This is the load-bearing path and the only one with a bespoke transport. `POST /api/proxy/chat` never
proxies straight through: `apps/web/src/app/api/proxy/[...path]/route.ts:936` diverts it into
`proxyChatWithWarmup`, which returns HTTP 200 immediately and emits SSE `status` events while the
user's Fly machine boots, then splices in the upstream stream. Consequence: **a failed chat request
still returns 200**, with the error arriving as an in-band `{type:'error'}` event.

## Overlapping / Duplicated Feature Areas

**1. `team` vs `team-2` — two generations, both alive.** `/team`, `/team/teams`, `/team/teams/[teamId]`
all render from `features/team-2` (163 files, 25k LOC). `features/team` (161 files, 29.6k LOC) has
**no route of its own** and survives as a parts bin: `campaigns/[id]/page.tsx:28` imports
`CampaignTeamManageModal`, `app/(auth)/onboarding/components/OnboardingChannels.tsx:7-8` imports
`SlackSetupDialog`/`TelegramSetupDialog`, and the sidebar, settings skills page, and
`features/spaces` chat views pull `AgentChatPanel`, `AgentCard`, and the voice components. A **third**
copy of the same concepts sits in `components/agents/{AgentInfoPanel,TeamModals,AgentActionsMenu}.tsx`.
`features/team-2/containers/Team2Container.test.tsx` even imports from `features/team`. Newer:
`team-2`. Wired to the UI: `team-2` for pages, `team` for modals and the agent chat panel.
**Verdict: LEGACY-in-migration, migration stalled.**

**2. `projects` vs `spaces` vs `campaigns` vs `programs` — one false overlap and one real one.**
`features/projects` is _not_ project management: it is an AI app builder (Sandpack editor,
`RepoImportModal`, `ProjectSupabasePanel`, `DatabaseBrowser`, publish to `{slug}-app.roas.io`). No
overlap with Spaces at all. The **real** overlap is `/campaigns` vs `/programs`: both call
`fetchPrograms()` from `lib/programs/programs-api.ts:56`, both render a list of `programs` rows, both
link to `/programs/{id}`, and each has its own messages config
(`campaigns/_config/campaigns-hub-messages.config.ts` vs `programs/_config/programs-index-messages.config.ts`).
`/campaigns`'s own `<title>` is "All Programs | ROAS". Meanwhile `/campaigns/[id]` is a genuine
_campaign_ page hitting `/api/campaigns/**`. So the `/campaigns` route serves programs at the index
and campaigns at the detail level. Newer: the Program concept (`programs` table, 2026 timestamped
migrations). Wired: both, from the same sidebar. **Verdict: DUPLICATED index, inconsistent route
namespace.**

**3. `composer` vs `studio` vs `artifacts` — not the overlap it looks like.** `features/composer` is
14 files of pasted-text chips for the chat input, consumed by `features/studio/components/ChatInput.tsx`
— a misleading folder name, not a content composer. `features/studio` is the _legacy Studio
workspace_: `/studio` redirects to `/team` and `StudioContainer.tsx` has zero importers, but the
folder is now the shared chat-runtime library (`use-chat-store` imported 30×, `campaign.service` 20×,
`chat.service` 12×) plus the funnel/presentation design-chat stores. `features/artifacts` is a
4-file global library page. **Verdict: no duplicated capability; one dead container inside a live
library, and one badly named folder.**

**4. `all-tasks` vs `my-work` vs `mission-control` vs `work-requests` — four projections, two dead
containers.** `space_items`, `mission_subtasks`, and `missions` are the shared substrate.
`/all-tasks` is the cross-space rollup (`GET /api/tasks/rollup`). `your_turn_items` (a 4-way
`UNION ALL` view) powers `YourTurnContainer` and `/home/inbox`. `features/my-work/MyWorkContainer`
composes `InboxListView` + `YourTurnSubtaskDrawer` into a third version of the same feed and is
imported by **nothing**. `features/mission-control/MissionControlContainer` is imported by nothing —
there is no `/mission-control` route — while the folder's `types` (51 imports) and `missions.service`
(26 imports) are heavily used by `campaigns/[id]` and `/home`. `work-requests` is genuinely distinct
(external token review). Newer: `all-tasks` + `your-turn`. Wired: `all-tasks`, `your-turn`,
`work-requests`. **Verdict: 2 DEAD containers, 1 real overlap (three renderings of "work assigned to
me").**

**5. `inbox` vs `channels` vs `dm` vs `notifications` — mostly distinct, but the inbox is implemented
twice.** `channels` = agent-participating rooms (`channels`, `channel_messages`); `dm` = human↔human
(`human_dm_*`); `notifications` = `user_notifications` rows. All three are legitimately separate. The
duplication is the _inbox surface_: `/home/inbox` renders `InboxFeed` from
`components/notifications/` (4 files), while `features/inbox` (7 files: `InboxContainer`,
`InboxListView`, `inbox-query`, `group-inbox-by-date`) and `features/notifications` (9 files:
`NotificationFeedRow`, `use-notifications-feed`, `notification-feed-filters`) implement the same feed
twice more. `InboxContainer` has zero importers; `InboxListView` is used only by the dead
`MyWorkContainer` and two home cards; `features/notifications` is used by exactly one home card.
Newer: `components/notifications`. Wired to the route: `components/notifications`.

## Feature Maturity Assessment

**Production-grade (five strongest).**

1. **Chat & agent runtime.** The only path with real engineering investment in failure modes:
   cold-start warm-up SSE, `[0,1,2,4,8,16]s` retry ladder, run resume via `agent_runtime_runs`,
   per-machine pinning with an explicit cross-tenant comment, after-the-fact cost reconciliation
   against OpenRouter, and a compatibility fallback that strips unrecognised gateway payload keys.
   Covered by `apps/web/e2e/chat.spec.ts` and 176 `features/studio` tests.
2. **Spaces.** 151 backend routes, 92 backend tests, 180 frontend tests, a real pluggable view
   registry, per-space schema JSONB, sharing at three granularities, advisory-locked recurrence
   generation. Biggest surface in the product and the one with the most consistent internal shape.
3. **Brain / memory.** One embedding dimension everywhere (768), paired semantic + `_lexical` RPCs
   for every entity, four cleanly separated Brain families, outbox-driven background consolidation,
   41 backend tests. `047_brain_consolidation.sql` shows a _completed_ migration — the V1 tables were
   actually dropped, which is rare in this repo.
4. **Missions.** Transactional outbox + `pg_notify` + BullMQ, idempotency keys, correlation ids,
   retry counts, parent/child DAG, DB triggers keeping `space_items.status` in sync. 30 backend tests.
5. **Integrations platform.** A genuine two-lane registry (Composio vs bespoke) driven off catalog
   tables rather than hardcoded branching, 94 backend tests, verified webhook signatures on 9 of 11
   receivers, and a DB-driven route config that lets agents reach legacy providers through the
   platform API.

**Prototype-grade (five weakest).**

1. **Flow builder.** 100 frontend files and a full clarification/evaluation build session model, but
   `flow_definitions`, `flow_definition_versions`, and `project_flow_action_promotion_candidate`
   are never read or written by any code, and the two definition tables form an insertable-only-with-
   deferred-constraints FK cycle. Authoring exists; installation does not.
2. **Autopilot / campaign strategy.** 6 files, 748 LOC, **0 tests**, no route, reachable only from a
   settings sub-page. `campaign_strategy_nodes` and `agent_awareness_points` have no test coverage.
3. **Social publishing.** The scheduler queue and UI exist, but `social_posts` and
   `social_post_schedules` have **no `CREATE TABLE` in `supabase/migrations/`** — they were created
   directly in production and only reconstructed in `scripts/roas/roas-drift-recovery.sql`. Same for
   `user_notifications`, which the inbox depends on.
4. **AI app builder (Projects).** No index route, `projects` table has **no RLS**, the published-app
   hosting branch in the Cloudflare Worker is dormant, the app→agent bridge
   (`POST /api/apps/:projectId/agent-call`) has no guard at all, and there are 2 backend + 1 frontend
   tests for a 30-file feature that embeds a code editor, a database browser, and GitHub import.
5. **Sharing (external).** `/shared/space` is deliberately stubbed while its `@Public()` backend keeps
   serving; `space_shares`, `space_item_shares`, `space_view_shares`, and `space_view_overrides` are
   four tables for one half-disabled capability.

**Two honest caveats on this assessment.** First, "IMPLEMENTED BUT UNVERIFIED" is the largest status
bucket here and it means exactly what it says — code exists on both sides and the wiring type-checks,
but nothing in the repo proves the path runs. Second, no live database, Vercel log, or Fly console was
available, so every runtime claim (which agent-api boot profile production uses, whether the nightly
billing cron actually 401s, whether the 45 no-access-path tables hold rows) is inference from source
and is marked UNKNOWN rather than resolved.
