🎙️ Meeting note takers: Fathom, Fireflies, Read.ai

Last updated: 2026-09-14 Category: Integrations Linear: ROA-40 · ROA-44 Source of truth: apps/api/src/modules/integrations/{fathom,fireflies,read-ai}, apps/api/src/modules/meetings, .docs/plans/meeting-notetaker-system-roa-40.md User's side: Features › Meeting note takers

How meeting recordings get from an AI note taker into ROAS, the three problems the old code had, and the modular system (ROA-40) that replaced them. Phases 0 to 4 are built, tested and pushed on branch claude/roa-40-modular-meeting-system; Phase 5, the live run with real accounts, is in review. Section 1 keeps the old pipes for the record; sections 3 to 6 describe what is built now. For the screens and what you can do, read Features › Meeting note takers.

📍 Paths starting with fathom/ mean apps/api/src/modules/integrations/fathom/, fireflies/ means apps/api/src/modules/integrations/fireflies/, meetings/ means apps/api/src/modules/meetings/, brain/ means apps/api/src/modules/brain/, web/ means apps/web/src/. The API adds /api in front of every route.

In one paragraph

Before ROA-40, two note takers were connected through two separate pipes: Fathom deep (recording lands in the brain, the Meetings space and the customer and campaign brains), Fireflies shallow (a brain job that never carried the transcript). Now there is one shared definition of a meeting, one front door every tool posts to, one brain import job, and Fathom, Fireflies and Read.ai are plug-ins behind it. The three problems below are fixed. What remains is the live run (Phase 5) and two production chores: apply the two migrations and run the Fathom re-registration script, after which the old Fathom door can go.

1 How it worked before ROA-40 (kept for the record)

Fathom: a real pipe with six exits. When a Fathom call ends, Fathom posts the recording to our webhook. We work out whose recording it is, fetch the transcript if the post did not include it, then fan out: brain import, customer-brain signal, Meetings space call row, Page Grader client match, Campaign Brain, and the post-call Slack flow downstream.

SituationDylan finishes a client call that Fathom recorded.
What happensFathom posts to POST /integrations/fathom/webhook. The service matches the header value against every connected user's stored secret, or, when there is no header, guesses the owner from the invitee emails in the body. If auto-ingest is on, it queues a fathom_meeting_import brain job, writes a customer-interaction row, creates or attaches a call row in the Meetings space, syncs to Page Grader, and routes matched clients to their Campaign Brain.
What you seeA call in Meetings with transcript and follow-ups, memories in the brain a minute later, and a Slack recap draft.

2 Three problems found, all fixed

Status 2026-09-14: fixed. Problem 1 by Phase 1 (the job payload carries the transcript: brain/services/brain-import-jobs-meeting-input.ts:37), problem 2 by Phase 0 (signature verified at the shared door: fathom/providers/fathom-webhook-signature.ts:11, rejected with 401 in meetings/intake/services/meeting-intake.service.ts:94), problem 3 by Phase 4 (ingest_meeting_transcript in apps/agent-api/src/modules/artifacts/services/artifact-brain-ingestion-actions.service.ts:441). The descriptions below are what was found on 2026-09-11.

Problem 1: Fireflies brain imports carry no text.

SituationAny Fireflies import, manual or sync.
What happensThe job payload is { transcriptId }. When the job is built for Atlas, the content extractor finds no transcript, no content, no text and no url, so it sends the whole payload as JSON. The transcript fetch that exists for Fathom is never run for Fireflies.
What you seeA "succeeded" job and a brain with nothing from the call.
Should beThe transcript is fetched from Fireflies before the job is queued and stored in the payload as speaker turns.
📍 Code: brain/services/brain-import-jobs-input.base.ts:81 · brain/services/brain-import-jobs-execution.base.ts:304 extractContentText · Fathom-only fetch :42 ensureFathomTranscript

Problem 2: the Fathom webhook does not verify the sender.

SituationAnyone posts a JSON body to the Fathom webhook route.
What happensThe header is compared to stored secrets as a plain string, not as a signature over the body. With no header at all, the owner is guessed from invitee emails in the body and processing continues. The route always answers 200.
What you seeNothing; that is the problem. A crafted body could create call rows and brain jobs for a user.
Should beFathom signs every delivery with webhook-id, webhook-timestamp, webhook-signature (HMAC-SHA256 over id.timestamp.body, 5-minute window). Verify it, reject the rest.
📍 Code: fathom/services/fathom-api.service.ts:138 resolveUserByWebhookSecret · fallback fathom/services/fathom-webhook.service.ts:412 resolveUserFromPayload · fathom/controllers/fathom-webhooks.controller.ts:84

Problem 3: the Fireflies agent action is empty.

SituationVibey decides to import a Fireflies transcript with its tool.
What happensThe action exists in the registry and the docs, but the handler takes no arguments and does nothing.
What you seeThe agent reports success; nothing is imported.
Should beOne provider-agnostic action, ingest_meeting_transcript, with schema, preflight and lifecycle per the agent tool rules.

3 The system in plain words (built)

One definition of a meeting. Title, time, attendees, transcript, summary and action items, in one shape no matter which tool recorded it. Meetings are the first kind; the shape also allows calls, recordings and uploads later.

One front door. Every tool posts to the same address, with a private key in the URL that names the connection. The plug-in for that tool checks the signature, a small table drops duplicates, and one intake service passes the meeting on.

One path into the brain. One job type, meeting_transcript_import, whose payload already holds the transcript. It replaces the Fathom-only job and the broken Fireflies one.

Plug-ins, not pipes. Fathom moves onto the new door and gains real signature checks. Fireflies gains a webhook and a working brain import. Read.ai joins as the third plug-in.

SituationA Read.ai meeting ends.
What happensRead.ai posts the full report to POST /integrations/meetings/webhooks/read_ai/<key>. The Read.ai plug-in checks X-Read-Signature with the signing key the user pasted, the delivery id is recorded, the report is normalized, and intake queues the brain job, writes the customer signal, and creates the call row.
What you seeThe same result as a Fathom call today: a call in Meetings, memories in the brain, a Slack recap draft.

4 How a user adds Read.ai

SituationNate uses Read.ai and wants his meetings in ROAS.
What happensIn Settings › Integrations he picks Read AI. The card shows his personal ROAS webhook address with a copy button. In Read AI › Integrations › Webhooks he creates a webhook with that address and copies the signing key Read AI generates. Back in ROAS he pastes the key and presses Connect. Read AI's "Send test request" button proves the link.
What you seeRead AI shows as connected; the next meeting arrives on its own. Read AI webhooks need a Pro or Enterprise plan.
Should beAs built, the ROAS address appears on the Manage row only after Connect, while Read AI hands out the signing key only once the webhook exists. The working order today is: create the webhook in Read AI with a placeholder address, copy the key, connect in ROAS, then edit the webhook address in Read AI. Showing the address before Connect is a logged follow-up and a Phase 5 check.

5 How any future tool joins

Only the shape of a meeting is fixed. How it arrives is the plug-in's business. A tool can join in four ways, and every way ends in the same intake.

TriggerWho starts itExamples
PushThe tool calls our per-connection URLFathom, Read.ai, Fireflies ping then fetch
PollOur scheduled sweep asks the toolZoom cloud recordings, any MCP-only server
User clickSomeone picks a meeting in Brain training"Import past meetings"
Agent actionVibey fetches through a tool and hands it overingest_meeting_transcript

A plug-in declares which of four capability groups it has: identity (name, login style), push (verify and parse a delivery), pull (list recent, fetch one, poll since a cursor), normalize. Login style can be OAuth, an API key, a pasted signing key, or an MCP session. Adding a tool later is one plug-in class, one catalog row, and one seed migration.

Contract and registry (built): meetings/providers/transcript-source.types.ts, transcript-provider.contract.ts:100, meeting-provider.registry.ts:14. Poll sweep follows brain/services/brain-import-jobs-runtime.base.ts:167. MCP is a pull transport; where its client runs (api or agent-api) is an open question in the plan.

? Questions people asked

Will the structure support any other system, not just the listed note takers? 2026-09-12
Yes for anything that delivers a transcript as text. The contract fixes only the shape of the result; how it arrives (push, poll, user click, agent action) and how you log in (OAuth, API key, signing key, MCP) are the plug-in's choice. Audio without text needs a transcription step first; that is a separate feature the contract leaves room for. 📍 .docs/plans/meeting-notetaker-system-roa-40.md "Extensibility Model"
Would it support an MCP connection? 2026-09-12
Yes, as a pull transport. An MCP server never calls us, so an MCP-backed tool joins through the scheduled poll, a user click, or the agent action; its plug-in implements the pull group with an MCP session instead of REST. Open question: whether that client runs in api or agent-api. 📍 apps/agent-api/src/modules/mcp/repositories/mcp.repository.ts
Where is testing in the delivery? 2026-09-12
Every phase has its own proof (section 6), and Phase 5 is a full-flow run with a real meeting recorded by all three tools, checked across Settings, Meetings space, brain, training panel, Vibey chat and the Slack flow. 📍 plan "Test Plan" and "Phase 5"
