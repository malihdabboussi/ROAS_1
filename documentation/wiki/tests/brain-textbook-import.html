✅ Check a textbook import end to end

Last updated: 2026-09-10 Category: Tests and checks Linear: ROA-9, ROA-18 Source of truth: local run on 2026-09-10 00:01 local, logs /tmp/roas-api.log, /tmp/roas-agent-api.log

Proves the whole "Train Brain" road on a laptop with no clicking: a job row goes in, the local api sweeps it, Atlas runs through the local gateway, the agent backend extracts entries with Gemini, and rows land in the textbook tables. Takes about 20 seconds when everything is local.

📍 Paths starting with brain/ mean apps/api/src/modules/brain/; agent-brain/ means apps/agent-api/src/modules/brain/.

1 Preconditions

  • Your own database and your own Redis. See Start here, section 7. A shared database or Redis makes this test meaningless: another api will take the job.
  • api on 3001, agent-api on 3003, gateway on 18789, all started from the main checkout with Node 22 or 23 from nvm.
  • Gemini key present in apps/api/.env. The agent backend reads that file as a fallback.
  • No leftover fingerprint for the text you will import. See step 4.

2 Steps

  1. Create a job row for the Default Brain with a short text, or re-arm an existing one: 
    update brain_import_jobs set status='retry', attempts=0, next_attempt_at=now(),
  last_error=null, result=null, started_at=null, completed_at=null where id='<job id>';
  2. Watch the status every few seconds: retry → processing → succeeded within about 20 seconds.
  3. Check the rows: one new ns_sk_sources row with status = completed and entries_count ≥ 1, and matching ns_sk_entries rows.
  4. Check the logs: agent-api prints [Artifact Stream] action=ingest_agent_brain_text then OK … durationMs= several thousand. A duration under 500 ms means the dedupe early-exit fired and nothing was ingested.

4 The failure modes this test catches

  • Fast fake success. Ingest returns OK in under 500 ms, no new source, job result says "already present". Cause: a leftover fingerprint in ns_content_hashes for this brain. The fingerprint is registered before the work, so one crashed attempt poisons all retries. Clear with delete from ns_content_hashes where brain_id='…', then re-arm. See Brain, Live finding 3.
  • Silent laptop. Job goes to processing and succeeds or retries, but no local log line appears. Cause: another api on the same database took it. See Live finding 2.
  • Source stuck at processing, zero entries. The ingest crashed after creating the source. The reason is in the agent-api log as a line starting "Failed to". No code marks the source failed.
  • Wrong process on a port. agent-api has no env file of its own and borrows the api's, including PORT. If apps/api/.env says 3001, a freshly started agent-api tries 3001 too. Give agent-api its own apps/agent-api/.env with PORT=3003.
  • "Bucket not found" after every Atlas run is the transcript upload to Supabase storage, which a restored local database does not have. Harmless for this test.
