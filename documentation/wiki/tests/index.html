✅ Tests and checks

Last updated: 2026-09-10 Category: Tests and checks Source of truth: apps/*/vitest.config.ts, playwright.config.ts, scripts/smoke, .claude/rules/testing.md

How we prove things work. There are five kinds of check in this repo. This page says what each one is, when to use it, the exact command, and the one workflow every change goes through so tests stay consistent with the system.

1 The five kinds of check

🧩 Unit tests

Small, fast tests of one function or service. The database and outside services are faked. Run them for the app you touched, not the whole repo.

pnpm --filter @vibey/api test
pnpm --filter @vibey/web test
pnpm --filter @vibey/agent-api test

To run one file or folder, add a path filter:

pnpm --filter @vibey/api test src/modules/brain
📍 Runner: Vitest. Config apps/api/vitest.config.ts (picks src/**/*.test.ts, fakes set in apps/api/src/test/setup.ts), apps/web/vitest.config.ts, apps/agent-api/vitest.config.ts. Brain tests live in apps/api/src/modules/brain/services/__tests__/.

🔗 Integration tests

Tests that call an API route end to end inside the process, still with a faked database. They live in one folder in the api app and run with the same command as unit tests.

pnpm --filter @vibey/api test src/test/integration
📍 apps/api/src/test/integration/, for example brain.integration.test.ts covering POST /api/brain/remember, POST /api/brain/search, GET /api/brain/stats, GET /api/brain/health, memory CRUD · contract tests in apps/api/src/test/contract/

🖥️ Browser tests

Playwright drives a real browser through the web app. Eight files cover login, chat, file upload, navigation, onboarding, studio, and team. They expect the web app to already be running on port 3000.

pnpm dev:app                       # terminal 1, leave running
pnpm --filter @vibey/web test:e2e  # terminal 2
📍 playwright.config.ts at repo root, tests in apps/web/e2e/*.spec.ts. Warning: the config has a webServer block that will start the dev server if none is listening, which breaks the "attach, never start" rule in .claude/rules/testing.md. Start the app yourself first.

💨 Smoke scripts

Scripts that poke a running system to confirm one flow still works: chat context window, customer signal loop, queue mixing, contacts, and one ClickUp task lifecycle. They need real services and are run by hand.

pnpm smoke:chat-context
pnpm smoke:customer-signal
pnpm test:e2e:task-sync
📍 Root package.json scripts smoke:* and test:e2e:task-sync · files in scripts/smoke/ and scripts/e2e/

👀 Static checks and the visual look

Type check, lint, and the architecture size check catch mistakes without running anything. The visual check is a person, or the assistant, opening the running app at three screen sizes and looking. Every commit runs the size check and the linter on the staged files automatically.

pnpm --filter @vibey/api typecheck
pnpm --filter @vibey/api lint
pnpm architecture:check
📍 Per-app typecheck and lint in apps/*/package.json · scripts/arch/check-loc.mjs · hook .husky/pre-commit · visual workflow is the test-improve command, which attaches to a running app and never starts one

2 The one workflow every change goes through

Use this order for any change, small or big. It matches the order the shipping command uses, so nothing is surprised at pull-request time.

  1. Say how you will know it worked, before coding. One line per acceptance rule: the route or command, the expected state, and the exact evidence. "Loads without error" is not evidence; "GET /api/brain/health returns 200 with memory_count > 0" is.
  2. Write or update the unit test next to the code. Same folder, .test.ts suffix. Fake the database like the existing tests do.
  3. Run the tests for that app only. pnpm --filter <app> test <path>. Red first if it is a bug fix, then green.
  4. Run type check and lint for that app. Web lint has known old violations on main; only new ones count.
  5. If a route changed, run the integration test for it, or add one in apps/api/src/test/integration/.
  6. If a screen changed, look at it. Start the app yourself, then run the browser tests or the visual check at phone, tablet, and desktop widths. Never let a test start a server.
  7. If it touches queues or outside services, run the matching smoke script against your local stack, never against staging or production with side effects.
  8. Write the doc and changelog, then commit. The commit hook runs the size check and linter on the staged files. Then open the pull request.

4 Ground rules

  • Browser tests attach to an app that is already running. They never start servers.
  • Anything that is not your own machine is read-only during tests. No submits, no sends, no purchases.
  • Every acceptance rule needs a deterministic way to know it passed: an exit code, a log line, a row in a table.
  • Scope test runs to the app you touched. Running everything through Turborepo is slow and some backend apps need secrets to even start their tests.
  • There is no CI workflow file in the repo. The pre-commit hook and the pull request review are the gates today.
