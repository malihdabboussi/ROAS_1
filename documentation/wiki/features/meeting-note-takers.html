🎙️ Meeting note takers, what you can do with them

Last updated: 2026-09-14 Category: Features Linear: ROA-40 · phases ROA-45 to ROA-50 · custom note takers ROA-51 Source of truth: apps/api/src/modules/meetings, apps/api/src/modules/integrations/{fathom,fireflies,read-ai}, documentation/features/integration-connections.md items 61 to 65 How it works inside: Integrations › Meeting note takers

This page is written from the user's side: connect a note taker once, hold your meetings, and find them in the Meetings space, in your brain, and in Vibey's answers. It describes the modular system delivered under ROA-40 on branch claude/roa-40-modular-meeting-system (Phases 0 to 4 built and tested; Phase 5, the live run with real accounts, is next). For the plug-in design and the evidence behind it, read the Integrations page.

📍 Paths starting with web/ mean apps/web/src/, api/ means apps/api/src/modules/, agent/ means apps/agent-api/src/modules/, migrations/ means supabase/migrations/. The API adds /api in front of every route.

In one paragraph

You connect Fathom, Fireflies or Read AI once in Settings › Integrations. From then on, every meeting that tool records arrives in ROAS on its own: it becomes a call row in the Meetings space with a transcript document and the follow-ups, it becomes memories in your brain, and it reaches the customer brain for the people who were on the call. You can also import a past meeting by hand from the Brain training panel, or ask Vibey to import one. All three tools go through the same door, so they behave the same way. A platform admin can add a fourth tool without code: press More integrations, pick Note taker, describe how the tool posts its meetings, test it on a sample, save. It then appears in the Library for everyone (section 7).

1 Connect a note taker in Settings

The point. Settings › Integrations lists Fathom, Fireflies and Read AI. Each connects differently because the tools differ, but once connected they are treated the same. Fathom logs you in with its own login page. Fireflies and Read AI give you a personal ROAS address to paste into the tool.

What happensFathom's login page opens; when he approves, ROAS stores the tokens, tells Fathom to send every finished recording to Dylan's private ROAS address, and creates the Meetings space for his workspace if it does not exist yet.
What you seeFathom shows as connected with the account name. Nothing to paste.

2 A meeting arrives on its own

The point. Whatever tool recorded the call, it posts to the same ROAS door. The door checks who the connection belongs to, checks the tool's signature, drops repeated deliveries, and hands the meeting to one intake that does the rest. You do nothing.

SituationDylan's client call ends. Fathom, Fireflies and Read AI all recorded it.
What happensEach tool posts to its own private address. The door looks up the connection from the key in the address (404 if unknown), asks that tool's plug-in to verify the signature (401 if wrong), reads the body (400 if unreadable), and records the delivery id (200 "duplicate" if seen before). Read AI's "meeting started" pings are answered 200 "ignored". Then the intake runs: if the tool only sent a ping (Fireflies), the plug-in fetches the full transcript; the meeting is normalized to one shape; a brain import job is queued; the customer brain is told; the Meetings space gets the call row. The tool receives 202.
What you seeNothing to do. Within a minute: a call in Meetings, memories in your brain, and the post-call Slack recap draft where that flow is set up.

3 Where the meeting shows up

The point. Three places, the same for every tool: the Meetings space, your brain, and the customer brain.

SituationDylan opens the Meetings space after the call.
What happensThe intake handed the meeting to the same Meetings route Fathom always used. It claims the event once per tool and meeting, finds the routing rules that apply (his own, or an admin's rule for his account or team), and creates or updates the call row: title, time, attendees, the transcript as a document that names the tool it came from, and the action items under follow-ups. If two tools recorded the same calendar meeting, they attach to one call row with one recording marked primary.
What you seeOne call row, not three, with the recordings listed, a transcript document headed with the tool's name, and the follow-ups. The Slack post-call flow, where set up, fires once for the row.

4 Import a past meeting by hand

The point. The Brain training panel lists your recent Fathom meetings and Fireflies transcripts; pick one and it is imported into the brain you chose. Read AI has no list because Read AI only pushes reports; its meetings arrive on their own.

SituationSara opens Train on an agent brain, picks a Fireflies transcript from last week, and presses "Add 1 to queue".
What happensThe panel asked the API which note takers exist and which are connected, so only connected ones are offered. The import call names the tool and the meeting id; the API asks that tool's plug-in to fetch the transcript, checks Sara may write to that brain and has credits, and queues the same "meeting transcript import" job the webhook path uses.
What you seeOne job in the tray, then the meeting's memories on the agent's graph.

5 Ask Vibey to import one

The point. Vibey has one action for meetings: "import meeting transcript", which takes the tool name and the meeting id. It works for Fathom, Fireflies and Read AI and replaces the old Fathom-only action and the Fireflies action that used to do nothing.

What happensVibey finds the meeting id, calls the action with provider "fathom", and the agent service asks the API's internal door to queue the same meeting import job. The action is declared with its schema, permissions and docs so the agent cannot call it with a tool ROAS does not know.

6 Disconnect

The point. Disconnecting removes the secrets and closes the door for that tool. The meetings already imported stay.

SituationSara disconnects Fireflies.
What happensThe API key and webhook secret are deleted from the vault and the connection is marked disconnected. The next delivery Fireflies sends to her address is refused with 404, because the door only serves connected rows. Read AI works the same way with its signing key; Fathom also deletes its webhook on the Fathom side.
What you seeThe card goes back to Connect. Call rows, documents and memories from earlier meetings remain.

7 Add a new note taker without code (platform admins)

The point. A note taker that posts JSON to an address can be added from Settings by describing it: what it is called, how it signs its deliveries, which event to accept, and where the meeting fields live in its JSON. The same door, brain import and Meetings route handle it from then on. Only platform admins see the button; everyone sees the result.

SituationDylan (platform admin) wants Otter meetings in ROAS. Otter is not in the Library.
What happensIn Settings › Integrations he presses More integrations. A row of type cards appears: Note taker is clickable, the other kinds (Social media, CRM, Payments, ...) say Coming soon. He picks Note taker. The fastest way is at the top: he pastes one delivery from Otter (most tools have a "send test request" button), presses Detect fields, and ROAS fills the paths and reports what it found and what is missing; or he picks a template (Read AI style, Fireflies style, simple speakers-and-text) from the dropdown. Otherwise he fills the form by hand: name and logo; the signature rule (which header carries the HMAC, hex or base64, an optional prefix such as sha256=, or "no signature"); which event to accept (for tools that also post "meeting started" pings) and the delivery-id field; and the field map, written as dot paths with [] for lists, for example transcript.speaker_blocks[].words. The mapping test runs on the same sample (Test mapping at the bottom re-runs it after edits): the panel shows the meeting id, title, number of transcript turns, the first turn, attendees and action items it found. He presses Save note taker.
What you seeThe dialog closes, the Library refreshes, and Otter sits under Productivity with its logo for every user. A user who presses Connect sees their personal ROAS address to paste into Otter first, then pastes Otter's secret and connects. Read AI and Fireflies now connect in the same order, which is what Read AI's own setup steps require (address first, key afterwards). Deliveries then flow like any other note taker.

Limits today. A defined tool must push JSON to an address; tools that need a login page or polling still need a code plug-in. Defined tools have no past-meetings list in Train and Vibey cannot import from them by id yet. Both are logged follow-ups.

Ids of defined tools start with nt_; api/meetings/providers/transcript-source.types.ts widens MeetingProviderId to built-ins plus that prefix, and meeting-provider.registry.ts resolve() asks the resolver for them with one database read per delivery, so an admin edit is visible on every API instance at once. Signature schemes: HMAC-SHA256 over the raw body (hex or base64, optional prefix, secret as text or base64) or none; Fathom-style Standard Webhooks is a logged follow-up.
