The brain in one paragraph

The brain is five kinds of notebook: yours, one per agent, one per campaign, one shared about customers, and one for the company. Knowledge enters through eight doors. Six of them write a ticket in the database, ring the Redis doorbell, get claimed by a worker, get read by Atlas, and get saved by a tool that fingerprints, extracts, embeds, and stores. Two doors, the ROAS Portal and chat, write directly. Everything lands on separate shelves: memories, textbook entries, snapshots, and the layers built from them. The web app, the Chrome extension, and the chat helper read those shelves back, and today the helper reads through a different copy of the search code, which is the biggest open problem.

🗄️ The database is the ticket

Everything that matters about a job is in the row: status, how many attempts, when to try again, the error, the result. Retry waits are computed here, not in Redis. If two processes share this database, they share the tickets, which is exactly Live finding 2.

📍 brain/services/brain-import-jobs-runtime.base.ts:404-408 markJobFailed · backoff table brain/services/brain-import-jobs.base.ts:174-183 · 🗄️ brain_import_jobs status check in migrations/20260303120000_brain_import_jobs.sql:8

🔔 Redis is the doorbell

Redis holds a repeating 3-second timer and one tiny note per due ticket. The note carries only the job id, one attempt, and is deleted when done. If Redis forgets everything, no job is lost: the next sweep reads the tickets again.

📍 brain/services/brain-import-jobs-runtime.base.ts:167-184 timers · :203-209 the note · Redis address order packages/api-shared/src/services/agent-runtime-queues.ts:28
SituationRedis restarts while three tickets are queued and one is processing.
What happensThe notes in Redis vanish. The three rows still say queued. When the api reconnects, the 3-second timer is registered again on start and the next sweep drops three fresh notes. The processing row keeps running; if its worker died, the 20-minute stale check moves it back to retry.
What you seeJobs resume within seconds. No duplicate rows, because the claim is one conditional update.

What fills these tables: Cortex Max. In one line: it keeps a brain thinking in the background, turning many memories into pages, timelines, and belief patterns, so the helper can answer about the big picture and how it changed over time. Crystallize, by contrast, goes deep on one text and writes one snapshot. A per-brain switch (ns_brains.cortex_max). Off, the brain only stores what you feed it. On, background jobs write narrative pages (the "library"), timelines, belief patterns and perspectives, and refreshed customer avatars. Switching it on queues a first full library sync; then every 10 new memories queues a library sync, every 5 changed pages a pattern analysis, and new customer memories an avatar pass. "Crystallize" forces a full rebuild. Jobs go through the brain-ops outbox and need a worker; on the local stack they never finish (see Issues).

What do "significance" and "confidence" mean, and who sets them? 2026-09-10

What is inside one memory row? 2026-09-10
Seen on the first locally saved memory. Who and where: brain_id the brain it belongs to, agent_id the helper that wrote it (Atlas for imports), speaker holds the user id despite its name, source_type/source_id/source_title the door and the job it came through. What it says: content is Atlas's rewording, not the user's exact sentence; memory_type one of fact, decision, insight, story, framework, preference, event; confidence 0.8 and significance 0.7 are the defaults; content_hash is the exact-duplicate fingerprint.
