# Loop Workflow Capability Inventory - June 22, 2026

## Architect Summary

Loop should not learn workflows by memorizing custom React forms or by inventing backend calls. The platform already has a large cabinet of agent actions. The missing product layer is a catalog card for each drawer: what it does, whether it can be used as a trigger or an action, which inputs it needs, what it outputs, how risky it is, and how the Flow UI should render it.

Right now the Flow builder has a small first-class trigger/action catalog, while the agent platform has a much larger action surface. That means Loop can build some flows directly, but many platform-capable workflows still require custom action registration before they can become durable, editable flows.

The right path is to make a Workflow Capability Graph from the existing agent action contracts. Most agent actions become candidate Flow actions. Triggers must come from event sources, not ordinary tools. Blueprints then compose triggers plus actions into reusable workflows, and the UI renders them from schema instead of hand-built forms for every step.

The main product rule: a capability is not Flow-ready until it has an execution schema, context contract, side-effect classification, approval policy, and UI schema. The tables below are the first-pass inventory from the current repo.

## Recommended Capability Contract

Every workflow-capable capability should add these fields on top of the existing action schema:

```ts
type WorkflowCapability = {
  capability_id: string
  source_action?: string
  kind: 'trigger' | 'action' | 'blueprint' | 'context_read' | 'control'
  family: string
  operation: string
  domain: string
  input_schema: Record<string, unknown>
  output_schema: Record<string, unknown>
  required_contexts: string[]
  produced_contexts: string[]
  side_effect: 'read_only' | 'platform_write_or_compute' | 'external_communication' | 'external_integration' | 'publish_external_or_public' | 'knowledge_write' | 'destructive'
  approval: 'none' | 'user_review' | 'admin_review' | 'blocked'
  executor: 'space_automation' | 'agent_action' | 'integration_event' | 'manual_review'
  ui_schema: FlowCapabilityUiSchema
}

type FlowCapabilityUiSchema = {
  icon: string
  summary_template: string
  fields: Array<{
    key: string
    label: string
    control: 'text' | 'template-text' | 'select' | 'multi-select' | 'resource-picker' | 'agent-picker' | 'connected-account-picker' | 'field-picker' | 'schedule-builder' | 'condition-builder' | 'date-time' | 'number' | 'toggle' | 'object-editor' | 'list-builder'
    required?: boolean
  }>
}
```

## Classification Rules

- **Triggers**: durable event sources only. Current examples are task events, form submission, contact events, artifact lifecycle, schedule, email/Slack/Fathom, and connected-app webhooks. Ordinary agent tools are not triggers unless they emit a durable event.
- **Actions**: executable backend actions that can run after a trigger. Most create/update/send/publish/ingest/execute agent actions are candidates.
- **Context reads**: read/search/list actions that produce context for later steps. They are useful inside Loop planning and sometimes inside flows if the runtime can store their output as step context.
- **Control actions**: Loop builder, MCP management, describe/search docs, team/skill/admin actions. These should not normally appear as user workflow steps.
- **Protected actions**: Atlas/HR/system-owned actions can be composed only through explicit delegation or a narrow approved Flow wrapper.

## Implementation Status

2026-06-22 19:44: Added the first shared `WorkflowCapability` contract in `packages/api-shared/src/types/workflow-capabilities.ts`.

This first slice wraps the current `FLOW_CAPABILITY_CATALOG` only. The grounded fields are the existing Flow capability ids, kinds, types, labels, categories, descriptions, required fields, optional fields, examples, and compatible trigger types. The wrapper explicitly marks these contracts as `catalog_fields_only`.

The generated UI schema, side-effect classification, approval policy, and contract gaps are deterministic defaults. They are not final authored contracts. Agent action schemas from `apps/agent-api` and `packages/agent-policy` are still documentation-only in this inventory until the next slice adds a backend-side generator or authored registry.

2026-06-22 20:05: Added the agent-api workflow capability graph in `apps/agent-api/src/modules/artifacts/services/artifact-workflow-capability-graph.ts`.

This slice combines compile-ready `trigger.*` and `action.*` Flow catalog entries with active policy agent actions exposed as `agent_action.*` candidates. Agent action candidates are generated from `ACTIVE_PROMPTMODE_ACTIONS`, `getActionContract`, and `ACTION_SCHEMAS`, preserving schema-backed required fields including one-of requirements.

The existing `get_flow_build_context` handler now returns `workflow_capabilities` so Loop can inspect platform-capable candidates before planning. Compile-ready Flow entries keep `execution.executor:"space_automation"` and `execution.status:"available"`. Agent action workflow steps use `execution.executor:"agent_action"` and are marked `execution.status:"needs_executor"` when they would need a Flow runtime bridge before durable compile/publish.

The platform API context service exposes the shared Flow-only workflow capability summary. It intentionally does not import the agent-api graph, because platform API should not depend on agent-api internals.

Loop guidance now tells agents to use `workflow_capabilities`, compile only `space_automation` entries directly, and request/draft a blueprint or runtime bridge for `agent_action.*` candidates instead of putting them directly into `create_flow_plan`.
