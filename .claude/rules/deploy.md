# Deploy rules

- **Presence of a deploy config file proves capability, not the live target.** roas-platform has `railway.json` for api/agent-api that are unused, and `.docs/deployment/backend-separation.md` describes a legacy VM topology. Verify with read-only provider calls (Railway MCP `get-service-config`, Vercel project links, env URLs) before writing a deploy map, and label unused configs as legacy. (source: codex-review 2026-09-02, finding 8)
- **Verified roas-platform map (2026-09-02):** web + api → Vercel (merge to `main` deploys; PR gives preview); agent-api/OpenClaw → Fly `roas-runtimes` via `scripts/roas/deploy-fly-runtimes.sh` only (never raw `flyctl deploy`); queue-worker + mission-worker → Railway project `roas-workers`, auto-deploy from `main`; apps-proxy → Cloudflare via `scripts/roas/deploy-apps-proxy.sh`. (source: Railway MCP + repo configs)
- **`/ship` never deploys.** Production deploys are a manual merge on GitHub or a manual script. A ship command stops at the PR and reports the preview URL. (source: user decision 2026-09-02)
- **`scripts/roas/deploy-railway-workers.sh` prints secret `KEY=value` pairs to stdout and does not deploy.** It is a manual human helper. Agents must never run it or paste its output into logs/chat. Railway workers auto-deploy from `main`; set variables in the Railway dashboard or via Railway MCP `set-variables`. (source: codex-review 2026-09-02 r2, finding 8)
